# 恢复机制详解

[返回文档中心](README.md)

## 目标

单账号逐段模式需要长时间运行。如果用户误关程序，服务器上的当前预约通常仍然存在，但本地计时会中断。恢复机制的目标是：

- 尽量保存当前预约和下一次扫描计划。
- 下次打开软件时先展示关闭前计划，由用户选择是否继续。
- 用户选择继续后，再查询服务器“我的预约”。
- 由用户确认是否接管自动换座。
- 避免只相信本地状态导致误取消或误换座。

## 状态保存时机

`ui/workers/alloc_worker.py` 会在以下阶段保存状态：

| 阶段 | `phase` | 内容 |
| --- | --- | --- |
| 第一段预约成功 | `waiting_next_scan` | 当前预约和下一次扫描时间。 |
| 等待下一次扫描 | `waiting_next_scan` | 当前预约、`notify_at`、后续预案。 |
| 找到下一段候选 | `pending_change_confirmation` | 当前预约、下一段候选、报告路径。 |
| 用户确认换座 | `changing` | 当前预约、下一段候选。 |
| 当前预约已取消 | `current_cancelled_booking_next` | 标记敏感阶段，便于重启后查服务器状态。 |
| 新座位预约失败 | `new_booking_failed_after_cancel` | 保留失败阶段和候选信息。 |
| 换座成功 | `waiting_next_scan` | 更新当前预约为新座位。 |

测试模式下的单账号续约预览只显示在界面上，不写入可恢复任务。只有真实预约成功后的单账号逐段任务才会保存恢复状态。

## 恢复时的判断顺序

1. 读取 `single_runtime_state.json`。
2. 检查 `active == true`、`mode == "single"`、账号是否匹配。
3. 软件启动后弹窗展示关闭前计划。
4. 用户选择“不管”时，清理本地恢复提示，不取消服务器预约。
5. 用户选择“继续计划”时，按保存配置启动单账号真实模式。
6. 登录当前账号，进入“我的预约”。
7. 查询服务器当前有效预约。
8. 如果服务器无有效预约，则按当前 GUI 配置重新开始。
9. 如果服务器有有效预约，则弹窗让用户选择继续、重扫或停止。

## 用户选择

启动时第一层选择：

| 选项 | 行为 |
| --- | --- |
| 继续计划 | 按关闭前配置启动单账号真实模式，并登录查询服务器预约。 |
| 不管 | 清理本地恢复提示；服务器上的已有预约保持不变。 |

登录并查询服务器后的第二层选择：

| 选项 | 行为 |
| --- | --- |
| 继续上次计划 | 接管当前预约；如果上次已有第二段候选，会立即重新扫描验证，并优先考虑该座位。 |
| 重新扫描 | 接管当前预约，但忽略上次第二段候选，立即按当前预约结束时间重新扫描。 |
| 停止 | 保留服务器当前预约，不继续自动换座。 |

## 为什么以服务器预约为准

本地状态可能在这些情况下过期：

- 用户关闭程序后手动取消了预约。
- 用户在网页端更换了座位。
- 程序在取消后、新预约前退出。
- 上次候选座位已被别人预约。

因此真正接管前必须先查询“我的预约”。本地状态只用来展示上次记录、兜底房间名、恢复计时计划和优先验证上次候选。

## 不建议手动编辑

`single_runtime_state.json` 是运行时文件。手动修改可能导致恢复提示不准确。若想彻底放弃恢复，可以删除该文件。
